# Перенос новой базы на существующий сервер

Подготовлено 2 ноября 2026 года по прямому поручению владельца. Это перенос текущего локального содержимого сайта в отдельную PostgreSQL-базу с последующим переключением `.env`, а не объединение со старыми серверными практиками. Прежняя база и файлы сохраняются для отката. Обычные обновления приложения по-прежнему не заменяют пользовательские данные.

3 ноября владелец поручил выполнить перенос самостоятельно; выпуск применён на прежнем адресе. Сохранённая прежняя база и полный backup находятся в `/root/ribkayoga-backups/release-20261102T183231Z`, активная новая база — `ribka_release_20261102_183231` (имена по UTC). [Фактическая проверка выпуска](VERIFICATION.md) описывает результаты. Повторно запускать импорт для уже перенесённого сайта не требуется.

Код, миграции и публичный начальный каталог находятся в Git. Приватный архив содержит аккаунт с прежним хешем пароля, текущие практики, разборы, скетчбук и все необходимые файлы. Он передаётся по SSH отдельно от репозитория. Серверные `APP_KEY`, адрес сайта, почта и реквизиты PostgreSQL сохраняются. Сессии, cache, задания и токены сброса пароля на новый сайт не переносятся; нужно войти заново.

## Подготовка снимка на компьютере

Готовый архив для этого выпуска находится в `.runtime/release-20261102/final/content.tar.gz`. Для нового снимка выбрать новую папку с последним компонентом `content`; существующий экспорт намеренно не перезаписывается:

```bash
python3 scripts/deploy/export.py \
  --database=/Users/Arago/Work/Php/RibkaYoga/.runtime/implementation-20261022/development.sqlite \
  --storage=/Users/Arago/Work/Php/RibkaYoga/storage/app/private \
  --output=/Users/Arago/Work/Php/RibkaYoga/.runtime/release-20261102/final/content
```

SQLite backup API создаёт согласованный снимок без изменения рабочей базы. В пакет входят `snapshot.sqlite`, переносимый `dataset.json.gz`, `manifest.json` с количествами и SHA-256, а также `files/`. Локальная `.env` и ключ приложения не копируются. Исходные файлы копируются с проверкой хеша; недостающий файл или ненулевые секреты 2FA останавливают экспорт. Архив и отчёт имеют закрытые права доступа.

Передать архив с компьютера:

```bash
scp /Users/Arago/Work/Php/RibkaYoga/.runtime/release-20261102/final/content.tar.gz \
  root@89.169.45.24:/root/ribkayoga-content-20261102.tar.gz
```

## Выполнение на сервере

Сценарий предназначен для существующей native-установки: `/var/www/reibkayoga`, локальный PostgreSQL, пользователь приложения `reibkayoga`, сервис `reibkayoga-php.service`. Требуются root, Git, PHP с PDO PostgreSQL и GD/FreeType, Composer, npm/Node, Python 3, PostgreSQL client tools и OS-пользователь `postgres`. Он использует существующее расширение `/opt/reibkayoga/php-extensions/usr/lib/php/20240924/pdo_pgsql.so` и проверяет, что OS-пользователь postgres подключается к тому же локальному кластеру.

В SSH-сессии root выполнить команды ниже. `FULL_COMMIT_SHA` заменить полным SHA опубликованного коммита из отчёта выпуска. Операторские скрипты извлекаются отдельно, чтобы резервная копия старого кода была сделана **до** обновления рабочего checkout:

```bash
cd /var/www/reibkayoga
git fetch origin main
RIBKA_TARGET=FULL_COMMIT_SHA
install -d -m 700 /root/ribkayoga-release-operator
git archive "$RIBKA_TARGET" scripts/deploy | tar -x -C /root/ribkayoga-release-operator
bash /root/ribkayoga-release-operator/scripts/deploy/server.sh \
  /root/ribkayoga-content-20261102.tar.gz "$RIBKA_TARGET"
```

Сценарий до изменения сайта проверяет чистую ветку `main`, точный SHA `origin/main`, происхождение скриптов, целостность архива, активную PostgreSQL-конфигурацию, `.env`, GD с FreeType и шрифт DejaVuSans. Новые пользовательские изменения в серверном checkout останавливают выпуск — их нельзя молча перезаписывать. Конфигурация с `DB_URL` или удалённым PostgreSQL требует отдельной адаптации; этот сценарий её не изменяет.

Затем сценарий:

1. Включает обслуживание и останавливает только выделенный PHP-сервис приложения.
2. Сохраняет PostgreSQL dump, `.env`, `storage/app`, старый код, frontend build и Git bundle в `/root/ribkayoga-backups/release-UTC_TIMESTAMP`, проверяет резервный dump и записывает SHA-256 архивов.
3. Обновляет код до заданного SHA, устанавливает зависимости по lock-файлам и собирает frontend.
4. Создаёт отдельную PostgreSQL-базу `ribka_release_YYYYMMDD_HHMMSS` с прежним владельцем. Миграции и импорт выполняются только в неё, независимо от старого config cache.
5. Импортирует данные транзакционно в порядке внешних ключей, восстанавливает self-links и числовые sequence. Проверяет состав таблиц, типы, количества, значения строк и SHA-256 файлов. Существующие неизменяемые файлы с другим хешем не перезаписываются.
6. Меняет только `DB_DATABASE` в `.env`, обновляет кэши и права, запускает PHP и до 30 секунд ожидает активный сервис и HTTP 200 у `/up` и `/login`. Начальный 502 до готовности FPM не прерывает публикацию.

В конце выводятся SHA кода, адрес сайта и путь к резервной копии. В этой папке находятся `import-report.json`, `verification.json` и приватные журналы. Пароли и ключ приложения в обычный вывод не попадают. Старые база и дополнительные медиа не удаляются.

## Откат

Если после полной резервной копии шаг завершится ошибкой, сайт останется на обслуживании, а сценарий напечатает точную команду:

```bash
bash /root/ribkayoga-backups/release-UTC_TIMESTAMP/operator/rollback.sh \
  /root/ribkayoga-backups/release-UTC_TIMESTAMP
```

Использовать фактический путь из вывода. Откат проверяет резервные хеши и отсутствие новых правок кода, возвращает прежние `.env`, код, зависимости и frontend build, обновляет кэши и запускает PHP. Старую базу не нужно восстанавливать из dump: она не изменялась. Новая база и добавленные файлы сохраняются для анализа. После отката Git будет в detached HEAD на прежнем SHA; ветка `main` сохранит новый коммит.
